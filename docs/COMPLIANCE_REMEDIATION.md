# Local compliance remediation candidate

This source branch is a local release candidate. It has not been deployed.

## Durable job cancellation prerequisite

LocalStore publishes mutations only after atomic persistence succeeds. Job cancellation therefore persists its terminal decision before aborting the Node HTTP request, waits for Node-owned work to settle, and prevents late stage updates from resurrecting a cancelled job. Repeated cancellation does not add another cancellation record or counter. A failed terminal-state write leaves the operation active and reports an error so the caller can retry.

This does not stop a remote Python worker process merely by aborting HTTP. It does not establish temporary-file cleanup, IPFS removal, copyright clearance, or a production retention guarantee. Those remain separate remediation gates. Do not delete job directories until worker quiescence is established.

Tests: tests/state.test.ts and tests/spatialRuntime.test.ts exercise durable state, failure/retry, cancellation ordering and Node task settlement. Synthetic fixtures only. No live storage changes are part of this patch.

Rollback: revert the candidate commits before release. Do not roll back durable-state semantics independently of callers that rely on committed snapshots. There is no production migration in this prerequisite.

## Journaled work-directory cleanup

New local attempts journal directory ownership before creating job files. They require worker cleanup protocol 1 and a worker instance identifier before processing. The instance is saved before HTTP submission. The worker persists cancellation tombstones and stops its process group before acknowledging quiescence. Cleanup rejects a missing, failed or mismatched acknowledgement, including a changed worker instance. Such cases retain files and a durable blocked status for operator review; a worker restart is not proof that a previous process stopped.

After success, failure or cancellation, Node attempts to remove only the journaled private/jobs/jobId directory. It preserves the original capture and Kubo outputs. Symlinks/junctions into another directory are rejected. Startup retries terminal cleanup; interrupted processing requires an explicit fresh attempt rather than silently restarting training. The authenticated POST /local/v1/jobs/cleanup route retries terminal cleanup and requires jobs:create in addition to jobs:read. Health reports cleanupPending and cleanupBlocked counts. Job cancellation now also requires jobs:create; read-only credentials cannot mutate jobs.

Existing unjournaled directories are not automatically deleted. Inventory them and approve a retention/ownership migration separately. Upgrade Node and the optional worker together; an older worker is refused for new jobs. Downgrading the worker alone cannot provide the acknowledgement required by the candidate. A changed-instance block needs evidence that the old process/container is stopped and a separately approved cleanup procedure, not a forged acknowledgement or manual change to the journal.

Verification includes synthetic filesystem failures, restart retries, missing/wrong worker receipts, preservation of captures, path/junction checks and isolated Linux process cancellation tests. Real CUDA reconstruction, deployed provider availability and remote-compute source cleanup are separate acceptance gates. Local temporary cleanup does not remove Kubo blocks, backups, independently retained copies or forensic remnants.

New processing requests are refused while a journaled cleanup is blocked. Retry cleanup or establish the missing worker/retention evidence before resuming. This gate does not constitute a review of legacy unjournaled files.

## Remote provider plaintext lifecycle

New provider records persist ownership, backend expiry, capture identity and input CID before pin/download/decryption. The local child ID is saved before a backend state transition; recovery also locates a child through its durable remote-job association. Preparation and cleanup share a completion barrier, so expiry/failure cannot delete files while decryption is still writing them. Cleanup requires child-worker quiescence before removing the owned remote-jobs directory and associated capture record. Original requester captures and generated Kubo outputs are preserved.

The local cleanup loop remains active while the provider is paused, disabled or denied backend authorization. It retries requested/expired owned records independently of backend polling. Terminal backend states and OUTPUT_READY also trigger reconciliation. Readable cleanup failures are recorded as blocked, and new assignments are declined while such a block remains. Status exposes aggregate computeCleanup counts; POST /local/v1/compute/cleanup requires compute:manage and retries requested/expired cleanup. Read-only capture credentials now also cannot invoke DELETE /local/v1/captures/:id; that operation requires captures:create.

The initial plaintext-cleanup prerequisite left input pin release pending. The coordinated managed-pin integration below now separates owner release from actual unpinning; legacy records and disabled release activation still retain pins. No independently retained ciphertext or output copy is promised erased. Existing legacy provider records without ownership evidence are not automatically adopted for deletion. The work directory is removed only after a verified same-instance worker acknowledgement or proof that no worker attempt began. Changed-worker instances and unknown historical files remain migration/operational gates.

Tests exercise early journal failure, download/decrypt failure, local insertion and backend transition failure, active preparation, missed child-ID persistence, restart/expiry, pause/offline/authorization failure, output-ready recovery, worker refusal, junction rejection and retry after filesystem failure. These are isolated tests, not a deployed provider or real-GPU acceptance record.

## Managed pin ownership prerequisite

ManagedPins records opaque owners before a pin operation and journals owner release before attempting an unpin. Equivalent CIDv0/CIDv1 identifiers share one key. Other archive, spatial and legacy private-input references protect a CID. Pins already present before adoption, and pins whose prior ownership cannot be determined, are retained rather than automatically removed. Failed releases remain pending across a restart. A generic missing RPC route is not treated as proof that a pin is absent. The initial ownership prerequisite did not migrate archive and compute callers. The subsequent coordinated integration below covers new pins in those paths; release activation remains disabled by default.

Official CLI writers now claim an exclusive lease beside the state file before initializing identity, credentials or mutable runtime state. A second writer is refused. The status and doctor commands read a snapshot without creating keys, directories or repairing a corrupt file; they remain available while the daemon holds the lease. Read-only stores reject updates. Short maintenance commands release their own lease when finished. Long-running commands retain it until a subsequent process can establish that the owner stopped, because deadline-limited shutdown can leave work in flight.

The lease uses a local filesystem atomic hard-link operation and host/process identity checks. It is not a distributed lock. Another host, an unobservable PID namespace, a malformed ownership file or an interrupted stale-owner recovery requires operator review. A replacement container can have a different PID namespace even on the same machine. Before release, document and test recovery after proving the former writer and all its workers stopped; never delete a live lease merely to bypass refusal. Existing older binaries and external code do not honor the new lease and must not write the same state concurrently. Hard-link support on the actual state volume is an activation requirement. No production state or lease has been changed.

Regression coverage includes a real synthetic child process, refusal while it is alive and recovery after its exit; same-process contention; unknown/malformed ownership; both diagnostic commands while a writer is active; failed journal writes; shared CID owners; withdrawal; restart retries; legacy-reference protection; and invalid CID rejection. Roll back this prerequisite only before dependent pin-flow changes, with the runtime stopped and state preserved. An already created ownership ledger is not evidence that legacy pins may be deleted.

## HTTP pin fallback integrity

The public archive HTTP fallback now imports returned bytes with pin=false, compares parsed canonical CIDs (including equivalent v0/v1 forms), and pins only after a match. A failed final pin is reported as failure rather than successful availability. Invalid requested identifiers are rejected before Kubo or gateway access. Existing addBytes callers retain their previous default unless they explicitly request an unpinned import. A mismatched gateway response may leave unpinned Kubo blocks; this correction does not perform garbage collection or promise forensic erasure. Existing pins are unchanged. This is one integrity boundary, not the complete spatial-manifest or managed-pin reconciliation fix.

The opt-in tests/managedPins.kubo.test.ts suite checks an explicitly identified disposable loopback Kubo peer before any writes. It exercises real unpinned imports, shared owners, failed-release persistence/restart, protection of manually pinned content, and both matching and mismatched HTTP fallback bytes. On 28 October 2026 it passed against an isolated offline Kubo 0.43.0 container with synthetic bytes; the owned container was stopped afterward. The regular suite skips this integration test unless both KUBUS_TEST_DISPOSABLE_KUBO_RPC and KUBUS_TEST_DISPOSABLE_KUBO_PEER identify such a fixture. Do not run it against an existing operator repository. No production pin, content or network was tested or changed. The standard smoke script still needs an isolated configured backend fixture; a missing local NODE_ENV prevents its execution, which is not a smoke pass.

Prior ownership checks request all pin types, including manual direct and indirect references. A recursive-only check could misclassify a previously direct-pinned CID as newly owned, so such pins are conservatively retained too. The default pinLs contract remains recursive for existing status and participation callers.

## Canonical pin-set generation protocol

The coordinated backend candidate returns a sha256 generation for the entire filtered eligible pin set, with count and page obtained in one PostgreSQL statement snapshot. Node requires the same generation on every page and checks it again before replacing its durable plan. Duplicate record IDs, incomplete responses, malformed generation values and a failed final confirmation leave the previous plan intact. A complete empty archive has a stable generation. An older backend without this field remains usable for additions, but Node clears any prior trusted generation; it must not be interpreted as authorization for removal.

The generation protocol alone does not authorize automatic unpinning. The subsequent integration below covers new archive, requester-input, provider-input and spatial-output references; activation still requires an exclusive managed Kubo repository and a review of legacy references. An archive-only ownership ledger cannot safely authorize removal while an untracked spatial writer can still pin the same CID. Durable backend snapshot grace-period reconciliation also remains open. Releasing a managed reference will not establish that independent copies disappeared.

Tests cover stable multi-page synchronization, same-count replacements, drift at final confirmation, offline confirmation, empty sets, legacy responses and preservation of the last committed plan on failure. Backend SQL was exercised with synthetic fixtures against disposable PostgreSQL 16; deployment requires checking database compatibility and query cost for the actual archive size. Old Node clients can ignore the additive generation field. Roll back the coordinated source changes before activation; no production database migration or pin mutation is part of this protocol change.

## Coordinated archive and compute pin ownership

New local spatial variants and manifests, encrypted requester inputs, provider inputs, retrieved requester outputs and canonical archive pins now acquire an explicit durable owner. Imports use pin=false before the ledger obtains the recursive pin. Output records retain their spatial owner identifier. Public archive owners are stable hashes of the record identity/version/role; removal of one public record does not release another record's owner of the same CID. Complete, generation-verified empty sets and replacements can relinquish obsolete archive owners. Legacy/incomplete canonical responses cannot do so.

All managed pin RPC calls use the canonical CIDv1 form. A disposable Kubo workflow exposed that retaining CIDv0 RPC calls in the HTTP fallback could create a second version-specific pin which CIDv1 removal did not remove. The fallback now uses the same canonical form. Existing v0 record URLs remain supported; pin discovery checks their v0 form first and retries the canonical form only after an explicit missing-pin response. Generic route/transport failures do not become successful alias lookups.

A provider input owner is relinquished only after its source preparation has settled and readable files have been cleaned following worker quiescence. Failed pin operations do not change successful plaintext cleanup back to a failure. Owner-release and pending-unpin journals are retried independently of provider pause, backend authorization and network polling. Legacy provider journals without pin ownership are retained for review. Requester cancellation requires the current backend-authorized terminal response and releases only its own owner. An ambiguous backend submission failure retains encrypted input and marks the submission for reconciliation: the server may already have committed the job. No retention deadline for that uncertain case has been invented; reconcile it against backend state before authorizing its eventual release. Invalid provider encryption keys are rejected before reading or importing captures.

`KUBUS_MANAGED_PIN_RELEASE_ENABLED` defaults to false, including an absent setting and the Compose templates. Owner relinquishment can be recorded while physical unpinning remains pending. Enable it only after confirming that this Kubo repository has one managed writer, older binaries and external/backend pin writers cannot race it, the state lease works on the actual volume, and legacy shared/manual references have been reviewed. This is a deployment/migration gate, not automatic proof obtained from a configuration flag. Pre-existing direct, indirect and recursive pins, unknown ownership, legacy private-compute references and recorded spatial references remain protected. No existing production setting has been changed.

Status includes only aggregate managed-pin counts. Compute cleanup distinguishes pending owner release, pending managed input unpins, unconfirmed requester submissions and legacy-review counts. A cleared owner-release flag does not mean Kubo blocks, backups or independent replicas were erased. Unpinning does not run garbage collection. Failed/partial spatial imports can leave journaled output owners requiring an explicit retention/deletion decision; they are not silently treated as canonical public records or automatically discarded by this patch.

Regression coverage includes initial/replacement/shared/empty archive plans, legacy and incomplete responses, activation defaults, persistent unpin failures, native filesystem restart cases, requester authorization/non-terminal refusal/shared-owner cancellation, failed submission, provider plaintext-versus-pin ordering, failed-release retry, and legacy preservation. The offline Kubo fixture verifies real shared ownership across archive reconciliation, requester cancellation and provider cleanup. It also verifies mismatched HTTP imports remain unpinned. These checks use synthetic content and do not establish deployed behavior, third-party retention, rights clearance or global erasure.

Rollback before activation can revert the coordinated source change with the runtime stopped and its state preserved. After any activation, first disable further releases and preserve the ledger and Kubo state for reconciliation; do not run old direct-unpin compute code against the same repository or discard ownership journals. Production rollback and legacy-data work require separate approval. The durable backend snapshot grace-period lifecycle, spatial rights clearance, manifest verification, account closure and final retention decisions remain separate open work.

## Unacknowledged unpin outcomes

An HTTP timeout or connection loss does not establish that an already submitted Kubo removal stopped. A local HTTP fixture demonstrates that the server operation can continue after the client has timed out. ManagedPins now durably enters releasing before the RPC. A transport failure, incomplete response, gateway 502/503/504 or otherwise unverified error leaves release_uncertain. Neither reacquisition nor another release of that CID is allowed; restart reconciliation does not replay releasing or release_uncertain entries. An acknowledged direct-RPC rejection remains eligible for ordinary retry. A crash or failed final state write can leave releasing and therefore also requires review.

Status exposes uncertainReleaseCount, and compute pending-input counts include those states. There is no automatic override or verified recovery button. The operator must establish that the former RPC writer and requests cannot still execute, reconcile actual Kubo pins and all valid references, and approve a specific recovery procedure. Merely waiting, observing a pin once, changing the activation flag or restarting only Node is not such proof. No production journal was changed. Existing older pin-release retry tests now explicitly model a completed RPC error; network-loss tests separately assert the fail-closed state and absence of new pin operations.
